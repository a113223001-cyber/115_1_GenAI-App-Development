## 二、輸出欄位契約

採用 Pydantic `BaseModel` 定義 `ProjectResult`，外層必須是物件，且必須包含下列五個欄位。`model_config = ConfigDict(extra="forbid", strict=True)` 表示拒絕多餘欄位與非指定型別；程式另外檢查文字不能為空或全空白。

| 欄位名稱 | 型別／限制 | 用途 | 畫面標籤 | 如何查原文 |
|---|---|---|---|---|
| `identified_meals` | `str`；必填、非空白 | 從輸入中辨識出的餐點與飲料項目，若無法辨識則填寫『資訊不足』 | 辨識出的餐點 | 檢查標籤中列出的餐點是否均可在原文中找到，確認模型無中生有未提及的食物。 |
| `estimated_calories` | `str`；必填、非空白 | 預估的熱量範圍（如：1500-1800 kcal），若無法估算則填寫『無法估算』 | 預估總熱量 | 對照原文中的餐點品項與估算份量，確認熱量範圍估算是否符合常理。 |
| `protein_assessment` | `str`；必填、非空白 | 蛋白質攝取量評估（如：足夠、偏低、過高、無法評估） | 蛋白質評估 | 檢查原文中是否有蛋白質來源食物（如蛋、豆漿、肉類），核對評估邏輯。 |
| `is_sufficient_info` | `str`；必填、非空白 | 輸入的內容是否包含足夠的飲食資訊以供分析（填寫『true』或『false』） | 資訊完整度 | 若輸入內容極度模糊，檢查此欄位是否精確設為 `false`，並確認畫面顯示警告。 |
| `dietary_advice` | `str`；必填、非空白 | 針對此飲食內容給出 1-2 點具體健康的建議，若資訊不足則提示使用者補充 | 營養師建議 | 核對建議內容是否切合該次飲食結構，或在資訊不足時引導使用者補充資訊。 |

處理順序是：檢查拒答與完成狀態 → 確認回應非空 → 解析 Pydantic 物件 → `check_result` 檢查欄位與型別 → 保存原文與結果 → 顯示。
結果保存在 `st.session_state.record`，不等於寫入永久檔案；畫面同時顯示當筆原文，方便人工回查。

### 3-1 雲端與真實 API 測試紀錄細節

本機真實 API 已完成兩筆；雲端真實 API 也已完成正常與資訊不足兩筆。以下內容皆為實際輸入與實際回傳，不是格式範例。

#### 案例 A：正常資料（本機真實 API）

- 測試日期：2026-11-09（台灣時間）
- 執行位置：本機 Streamlit
- 設定模型：`gpt-5.4-mini`；畫面回應未顯示模型 ID，若正式紀錄需再確認實際呼叫模型
- 完整原文：「早餐吃鮪魚蛋餅配無糖豆漿，午餐吃排骨便當飯半碗」
- 實際 API 請求數：1 次
- `max_retries`：0
- 實際輸出：

```json
{
  "identified_meals": "早餐：鮪魚蛋餅、無糖豆漿；午餐：排骨便當",
  "estimated_calories": "約 800-1100 kcal",
  "protein_assessment": "蛋白質攝取尚可，早餐與午餐皆有蛋白質來源，但午餐若排骨份量偏少則可能略不足",
  "is_sufficient_info": "true",
  "dietary_advice": "這份紀錄已有基本餐點資訊，可再補充份量與便當配菜，會更有助於估算熱量與蛋白質是否足夠。"
}
```

人工逐欄核對：

| 欄位 | 判讀 |
|---|---|
| `identified_meals` | 鮪魚蛋餅、無糖豆漿與排骨便當均可對應原文。 |
| `estimated_calories` | 熱量為粗估；原文未提供晚餐、詳細份量與配菜，範圍仍需人工核對。 |
| `protein_assessment` | 論述有蛋白質來源依據，排骨份量不足時可能略低；沒有編造具體數值。 |
| `is_sufficient_info` | 原文已有兩餐的基本資訊，填寫 `"true"` 合理。完整營養分析仍缺份量與配菜。 |
| `dietary_advice` | 建議補充份量與便當配菜，對應原文缺少的資訊，沒有加入未提供的晚餐。 |

結論：格式與內容基本合理；原文沒有晚餐，因此回傳沒有編造晚餐。熱量與蛋白質評估仍屬粗估，需人工核對份量與配菜。
